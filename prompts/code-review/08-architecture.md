## 架构检查规则（Architecture）

### 重点检查

- 边界与分层
  - 业务层/应用层/基础设施层是否边界清晰；依赖方向是否单向（高层不依赖具体实现细节）
  - Web/Handler 是否过胖；是否把业务逻辑下沉到可复用的 domain/service
  - 是否在 controller/handler 中混入 service 业务逻辑（编排、校验、事务、权限等），导致层次边界被破坏
- 域划分与上下文边界
  - 是否有清晰的域划分（业务域/子域/限界上下文）；跨域交互是否通过明确的接口或防腐层
  - 领域模型与应用编排是否分离，避免把编排逻辑揉进领域对象
- 模块依赖与耦合
  - 模块之间是否存在循环依赖；是否有“全局工具类/公共包”不断膨胀
  - 关键抽象是否稳定；是否出现到处传递的巨大 DTO/Context
- 数据泥团与职责混杂
  - 是否存在数据泥团（Data Clump）：一组字段/参数在多处以相同组合反复出现，暗示缺失合理抽象
  - 是否存在混合职责类（Mixed Responsibilities）：同一类同时承担业务规则、编排、持久化、网络调用、格式转换等多种职责
  - 是否存在“上帝对象”持有过多依赖与数据，成为变更与耦合中心
- 数据与领域建模
  - 核心实体与聚合边界是否合理；读写模型是否混杂导致复杂度飙升
  - 事务边界是否明确；跨边界写入是否可控（最终一致性/补偿）
- 类划分与设计原则
  - 类/接口职责是否单一，是否符合 SOLID（尤其是 SRP/OCP/LSP/ISP/DIP）
  - 是否遵循 DRY；重复逻辑是否可被抽象到稳定的边界内
  - 设计模式使用是否恰当（避免为模式而模式）；是否存在过度抽象
  - 领域模型是否“充血”（行为与规则聚合在模型/领域服务中），避免贫血模型把规则散落各处
  - service 是否过于庞大（上帝服务），是否需要拆分为更小的领域服务/应用服务/工作类（worker/usecase）
  - 是否存在平行继承体系（parallel inheritance）导致变更需要同步修改多条继承链
  - 是否存在冗余类/过度拆分（仅转发调用、无领域含义），导致理解与维护成本上升
- 函数结构与表达一致性
  - 函数命名/注释/文档与实际逻辑是否一致，避免“名不副实”造成误用
  - 函数结构是否清晰（单一职责、可拆分），是否存在过深嵌套与高圈复杂度
  - 关键分支是否可读（早返回、提炼函数、守卫子句），避免难以维护的嵌套金字塔
  - 是否存在大量 switch/case（或 if-else 链）导致复杂度上升，是否可用多态/策略/表驱动收敛分支
- API 规范与返回一致性
  - API 是否遵循同一规范（路径/命名/版本/分页/错误语义）；返回值格式是否一致
  - 返回内容是否完整（必要字段、错误详情/追踪信息、分页元信息），并与文档/契约一致
  - 错误码/异常语义是否统一，避免同类错误多种表达
- 可扩展性与演进
  - 是否支持横向扩展（无状态、幂等、外部依赖可替换）
  - 新增需求的改动面是否可控；是否存在“改一处牵一片”的结构性问题
- 可观测性与故障隔离
  - 是否在关键边界点有统一的日志/指标/追踪埋点与错误分类
  - 依赖故障是否隔离（超时、限流、熔断、舱壁）；是否会级联故障
- 微服务韧性治理
  - 是否有合适的降级策略（兜底数据/默认值/静态页/功能开关），并能明确区分“可降级”和“不可降级”能力
  - 熔断/隔离/重试策略是否合理（阈值、半开、退避、抖动），是否避免重试放大与级联故障
  - 是否有分级保护：核心链路优先、非核心限流或降级；是否支持按接口/租户配额
- 解耦机制与全局异常处理
  - 是否通过注解/声明式机制降低耦合（例如事务、鉴权、校验、限流、缓存等横切关注点），并避免滥用导致行为隐式化
  - 是否有全局异常处理器统一转换错误响应，避免到处 try/catch 与重复返回结构
  - 是否采用异常机制表达失败路径，而不是用 return code 充当控制流（除非项目规范明确要求）
- 事务边界与一致性
  - 是否有清晰的 Transaction 边界（通常在应用服务层），避免把事务散落在 controller 或 DAO 中
  - 跨多个写操作时是否使用事务保证一致性；异常路径是否能回滚；是否避免长事务与锁放大
- Redis 缓存与 MQ 的架构使用
  - Redis：是否适合做缓存/会话/分布式锁；TTL/淘汰/预热策略是否明确；是否处理穿透/击穿/雪崩
  - 一致性：缓存与数据库的一致性策略是否明确（旁路缓存/写穿/写回）；是否有失效顺序与回源保护
  - MQ：是否用于异步解耦与削峰；是否有消息幂等、去重、顺序、重试与死信队列策略
  - 投递语义：至少一次/至多一次/恰好一次的假设是否被代码与测试验证；是否有可观测性与积压告警

### 常见高风险信号

- 领域规则散落在 controller/handler、ORM hook、工具函数中
- controller/handler 承担过多业务编排与校验逻辑
- 超大 service 类/方法簇堆叠，难以复用与测试
- 多步写操作缺少事务保护，异常时产生部分写入与数据不一致
- 上帝类/超大类/超大接口；一个类承担过多职责
- 贫血模型：实体只有 getter/setter，规则散落在流程代码里
- 重复逻辑以多种相似实现存在（难以统一修改与回归）
- 设计模式堆叠导致理解成本高，但收益不明确
- 函数名与内容不一致，或对外语义与内部行为不一致
- 嵌套过深、圈复杂度过高导致改动风险大且难测试
- 平行继承体系：新增一个类型需要在多处继承层级同步添加类
- 冗余类/无意义抽象：大量薄封装与转发类，改动扩散且难定位责任
- 业务分支靠超长 switch/case 维护，新增分支需要改动多个位置
- 硬编码（magic number/string、枚举映射、配置常量写死）导致不可配置、不可扩展、难以迁移
- 数据泥团：一组字段在多个方法/DTO 中成组出现，但没有对应的值对象/领域概念
- 混合职责类：一个类同时处理业务、IO、持久化、协议转换，导致难测试且易改坏
- API 返回结构不一致，同类错误在不同接口里表现不同
- 失败路径用 return code 蔓延，调用方到处写 if/else 分支处理
- 缺少统一异常处理，导致错误响应/日志/指标分散且不一致
- 缺少降级与熔断，外部依赖抖动时出现级联故障
- Redis 作为“万能存储”滥用，或 TTL/淘汰策略缺失导致内存与一致性风险
- MQ 无幂等/无去重/无 DLQ，失败后消息丢失或反复消费造成数据污染
- 大量跨模块的直接调用与数据结构互相渗透
- 基础设施细节（HTTP/DB/Cache SDK）泄漏到业务核心
- 新功能只能“复制粘贴一条链路”才能落地

### 需要给出的证据

- 模块依赖图/调用链中的不合理依赖（文件/包/层级）
- 类/接口责任不清的证据（方法簇、字段簇、变更原因）
- API 契约不一致的证据（返回结构对比、错误语义对比、缺失字段）
- 缺少全局异常处理器或注解机制使用不当的具体位置
- 降级/熔断/重试策略缺失或不当的证据（配置、拦截器、客户端封装、关键调用点）
- Redis/MQ 使用不当的证据（缓存键/TTL、回源逻辑、幂等键、消费重试、DLQ）
- controller/service 层次边界被破坏的证据（业务逻辑落点、调用链、重复校验）
- 事务缺失或事务边界不当的证据（多步写入、异常回滚、长事务）
- 平行继承体系与冗余类的证据（类层级对照、重复变更点、仅转发的薄封装）
- switch/case 复杂度上升的证据（分支数、重复逻辑、违反开闭原则的改动点）
- 硬编码的证据（魔法常量位置、重复字面量、配置缺失点）
- 数据泥团/混合职责类的证据（重复字段组、过多构造参数、类依赖与职责清单）
- 改动扩散示例（一个需求导致多处重复改动）
- 可观测性缺口（关键链路缺少指标/追踪/错误分类）

### 建议输出应包含

- 修复策略：明确分层与依赖方向、抽象收敛、拆分模块、引入接口隔离、收敛重复逻辑与稳定抽象
- 验证建议：架构测试/依赖约束（禁止依赖）、关键链路端到端回归
