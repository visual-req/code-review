## 测试与可验证性检查规则（Testing）

### 重点检查

- 关键路径覆盖
  - 鉴权/授权、支付/计费、数据写入、状态转换、外部调用边界
  - 边界输入与错误分支（超时/异常/重试/幂等等）
- 测试类型是否合理
  - 单测：纯逻辑、边界、错误契约
  - 集成测：数据库/缓存/消息队列/第三方依赖
  - E2E：关键业务链路（少而精）
- 测试分组与映射是否清晰
  - 测试用例是否按模块/能力/场景分组，命名是否表达意图
  - 测试是否正确映射到需求/缺陷/风险点（为什么要测、覆盖哪个分支/不变量）
  - 是否避免跨层混测导致定位困难（单测里引入大量外部依赖）
- FIRST 原则
  - Fast：单测是否足够快，是否存在不必要的 IO/睡眠
  - Independent：是否存在顺序依赖、共享状态、对环境有隐式依赖
  - Repeatable：是否不依赖网络/时间/随机性/外部服务，能稳定复现
  - Self-validating：断言是否明确，避免靠日志/人工判断
  - Timely：关键逻辑是否及时补测，回归是否覆盖变更点
- 测试数据与夹具稳定性
  - 测试数据来源是否稳定（固定 fixture/可控工厂），避免依赖线上/共享环境数据
  - 是否能在测试内构造最小数据集；是否避免超大样本导致脆弱与慢
  - 数据清理是否完整，避免污染后续用例
- 可测试性设计
  - 依赖注入、接口隔离、可替换时钟/随机数/IO
  - 避免全局状态与不可控副作用

### 常见高风险信号

- 只测“成功路径”，不测失败/异常/边界
- 大量依赖真实外部系统导致测试不稳定
- 无法在测试中控制时间与随机性
- 用例之间共享数据/顺序依赖，或依赖固定执行顺序才通过
- 测试命名/分组混乱，无法看出覆盖的需求与风险点
- 断言弱（只看日志/只 assert 不崩溃），导致误报与漏报

### 需要给出的证据

- 缺失测试的关键模块与风险点
- 测试不稳定的原因（共享状态、顺序依赖、时间敏感）
- 用例分组与命名无法映射到模块/需求/缺陷的具体例子
- 测试数据来源不稳定的具体点（外部服务、共享库、随机性、时间）

### 建议输出应包含

- 增测策略：优先补高风险单测与关键集成测
- 验证建议：给出可复现步骤与断言点，避免“看日志判断”
- 结构建议：按能力/场景分组测试，建立需求/风险点到用例的映射（最少保证关键链路可追溯）
